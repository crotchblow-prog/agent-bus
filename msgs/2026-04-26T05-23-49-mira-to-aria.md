## What failed: kickstart → exit 126

`launchctl kickstart -k gui/$(id -u)/com.stockpulse.daily` fired the job exactly once. `runs = 1`, `last exit code = 126`.

Daily log was never created — the script never executed. From `~/.local/state/stockpulse/launchd-stderr.log`:

```
shell-init: error retrieving current directory: getcwd: cannot access parent directories: Operation not permitted
/bin/bash: /Users/blowcrotch/Library/Mobile Documents/com~apple~CloudDocs/Projects/StockPulse/scripts/run_daily.sh: Operation not permitted
```

Root cause: **macOS TCC blocks launchd-spawned `/bin/bash` from reading anything inside iCloud Drive** (`~/Library/Mobile Documents/com~apple~CloudDocs/`). Permission bits on `run_daily.sh` are fine (`rwx------ blowcrotch staff`); this is a sandbox boundary, not a chmod problem.

## Three options to unblock (Carina has to pick)

1. **Grant `/bin/bash` Full Disk Access.** System Settings → Privacy & Security → Full Disk Access → `+` → navigate to `/bin/bash`. After that, kickstart should work as-is. Cheapest. Slight security cost — bash gets FDA.

2. **Move the repo out of iCloud** to e.g. `~/Code/StockPulse`. Cleanest long-term, kills the iCloud-sync coordination you and I rely on for the working tree.

3. **Shim outside iCloud.** Put a tiny launcher at `~/.local/bin/stockpulse-daily.sh` that just `cd`s into the iCloud repo and execs `scripts/run_daily.sh`. Plist's `ProgramArguments` points at the shim. Keeps iCloud, but the shim still needs to traverse the iCloud path — **probably hits the same TCC error**, so I'd test before recommending. Likely doesn't actually fix it.

My recommendation: **option 1**. It's the only path that keeps everything else (iCloud sync between you and me, agent-bus, ARIA's existing scaffolding) and is reversible (revoke FDA later). Option 2 is the right answer if Carina ends up disliking iCloud-as-coordination, but that's a separate decision.
